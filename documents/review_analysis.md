## Issue-by-Issue Analysis

### 🔴 CRITICAL — Will cause desk reject or strong reject

**C1. Placeholder values throughout the draft**
- Both reviewers flag `[X]`, `[T_angr]`, `[N_modbus]`, `[P_semantic]` as desk-reject triggers.
- **Status**: True. These are intentional draft markers but must all be filled before submission.
- **Fix**: Run the full experiment matrix. These numbers are obtainable now.

**C2. Autonomy contradiction — Level 3 requires user-supplied mutator**
- DeepSeek: "the core claim is false."
- Grok: "remove 'autonomous' if any manual setup is needed."
- **Status**: True and serious. The current framing ("autonomous … without human intervention") is undermined by Level 3's optional pre-supplied mutator. The mutator is a *user-provided artifact*, not generated by the system.
- **Fix options**:
  1. **(Preferred)** Reframe: Level 3 is a *user-assisted optimization*, not a core autonomy claim. Autonomy applies to Levels 1+2 (stall detection → Z3 solve → payload injection). Level 3 is described as an optional extension that requires domain knowledge to implement once but runs continuously thereafter.
  2. **(Stronger)** Implement auto-generation: from the Z3 model's structure (detected as CRC-32 via `BITWISE_LOOP + INDEXED_LOOKUP`), auto-synthesize a Python mutator stub that calls `zlib.crc32` at the correct frame offset. This is ~50 lines of code and makes the claim fully defensible.
  - Recommendation: **Do both** — implement auto-synthesis for the CRC-32 class (demonstrable in the evaluation), and reframe Level 3 as "autonomous for recognized constraint classes, user-extensible for novel ones."

**C3. "Converged in 1 turn for all 10 targets" — asserted without evaluation**
- DeepSeek: "reads as an unsupported promise."
- Grok: "suspiciously convenient."
- **Status**: True. This claim is based on the ICS CRC-32 telemetry (`react_turns_total=1`). The other 9 targets have not been run yet.
- **Fix**: Either soften to "converged in 1 turn for our primary benchmark" or run the full matrix and report the distribution.

### 🟡 SIGNIFICANT — Will generate major revision requests

**S1. Offset probing soundness**
- Both reviewers: brittle, heuristic, will fail on optimized/stripped/struct-passing code.
- **Status**: Partially true. The heuristic works on all 10 evaluation targets (all compiled with `afl-clang-fast`, standard x86-64 ABI, symbols present). It would fail on stripped firmware blobs.
- **Fix**:
  - Expand §3.7 limitations to explicitly scope the claim: "this heuristic is valid under standard AFL++ compilation with `afl-clang-fast` and the System V AMD64 ABI, which all evaluation targets satisfy."
  - Add a quantitative result: report the match score (13/15 bytes matched for ICS CRC-32) across all 10 targets.
  - Add a fallback path: if no register matches within threshold, fall back to full-frame payload construction using the first 64 bytes as the constraint window (conservative but safe).
  - This does NOT require replacing the heuristic — just bounding its claims properly.

**S2. CARM closed-world generalization claim**
- DeepSeek: "retrieval is evaluated in a closed-world setting."
- Grok: "nearest-neighbor is basically glorified few-shot."
- **Status**: Valid concern. Templates come from the same 10 targets.
- **Fix**:
  - Design a held-out experiment: seed CARM with 8 targets, run on 2 held-out targets. Report whether Jaccard retrieval finds a useful template (even if not from the same algorithm family).
  - Report retrieval precision at θ=0.30 vs θ=0.50 across the target matrix.
  - Acknowledge explicitly in §3.5 that with a larger production deployment, micro-harvesting is expected to improve retrieval quality.
  - The "15-tag ontology is coarse" concern is accurate but manageable — this is a design tradeoff, not a flaw.

**S3. Stall detection parameters are arbitrary (300s, 10 cycles)**
- Grok: "arbitrary. False positives/negatives?"
- **Status**: True — these are empirically derived defaults, not formally justified.
- **Fix**:
  - Add a sensitivity analysis: report whether different $\Delta_{\text{stall}}$ values (180s, 300s, 600s) change bypass outcomes. This is cheap to run.
  - Note that the time-based threshold is user-configurable via `--stall-minutes`, so it's not hardcoded.

**S4. §3 reads like a tool description in places**
- Grok: "elite venues want deeper invariants, failure models, and worst-case analysis."
- **Status**: Valid. Paragraphs citing `O_WRONLY|O_CREAT|O_EXCL` and `asyncio.create_subprocess_exec` belong in §4 Implementation.
- **Fix**: Trim implementation minutiae from §3, move to §4. Strengthen §3 with formal invariants (e.g., "the agent maintains the invariant that no AFL++ process modification occurs until a SAT verdict is confirmed").

**S5. CmpLog claim ("makes no progress on CRC-32") in §2.3 is an empirical assertion without data**
- DeepSeek: "belongs in evaluation, not motivation."
- **Status**: True.
- **Fix**: Add "(confirmed in §5.2)" forward reference, or rephrase as "the input-to-state correspondence mechanism cannot, by construction, satisfy polynomial constraints [Redqueen] — a point we confirm empirically in §5.2."

**S6. Novelty — "incremental" risk**
- Grok: "pieces exist in prior work (LLM-Sym, TDD_v2, HyLLfuzz). Need a sharper delta."
- **Status**: Valid risk. The sharpest delta is the *closed-loop, zero-human-intervention integration*. No prior work does the full pipeline: runtime stall detection → extraction → retrieval → solving → injection → escalation in a single autonomous system.
- **Fix**: Sharpen §1 contribution list to lead with "autonomous closed-loop integration" rather than the individual components. Add one sentence: "Crucially, no prior system performs stall detection, constraint solving, and coverage escalation within a single autonomous co-process — prior work requires human orchestration of individually capable but disconnected components."

### ⚪ FALSE POSITIVE — Reviewer is wrong

**F1. "AFL++ `-F` flag does not exist"** *(DeepSeek, §3e)*
- **Status: Factually incorrect.** DeepSeek's claim is wrong.
- Verified: `afl-fuzz --help` confirms: `-F path — sync to a foreign fuzzer queue directory (requires -M, can be specified up to 32 times)`.
- This is the correct mechanism for importing corpus entries from external processes in AFL++ 4.x.
- **Action**: No change to the paper. This claim can be dismissed. However, add a footnote or inline citation to the AFL++ 4.x documentation to preempt this confusion from real reviewers: "using AFL++'s `-F` foreign sync directory mechanism [AFL++], which provides one-way corpus import from an external process without shared memory."

**F2. "Autonomy requires no manual harness compilation"**
- Both reviewers partially conflate two different things: (a) the agent's runtime autonomy and (b) the user's one-time setup.
- **Status**: This is a framing issue, not an architectural flaw. All systems research requires one-time setup. AFL++ itself requires manual harness compilation. The autonomy claim applies to the *runtime pipeline*, not the build system.
- **Action**: Add one clarifying sentence in §1: "Agentic-AFL does not abstract harness compilation — users compile targets with standard AFL++ instrumentation, consistent with the UNIX philosophy of composable tools. Runtime autonomy refers to the agent's zero-intervention operation after campaign launch."

## What the Reviews Got Right (Internalize These)

1. **"+1644% is marketing without §5."** They're correct. Never put a % gain in an abstract without the full evaluation behind it at submission time.
2. **"Reads like a tool description."** §3.1 and §3.3 have too many implementation verbs. Systems papers describe *what the system guarantees*, not *which Python function calls what subprocess*.
3. **"CARM closed-world."** This is the most substantive scientific concern. The held-out experiment (Phase 2, item 4) is essential.
4. **"Agentic is a buzzword."** They're right that the bar is higher now. The contribution framing must emphasize the *integration architecture* and *closed-loop feedback*, not the LLM component.

## What the Reviews Got Wrong (Rebuttal Points)

1. **"-F flag does not exist."** It does. Documented and verified.
2. **"Autonomy violated by harness compilation."** Category error. All tools require build-time setup.
3. **"13 LLM calls per stall."** Misread: K=3 parallel + up to 5 ReAct turns = *at most* 18 calls, but in practice the loop exits on first SAT (1 turn = 3 calls on the primary benchmark). The abstract's "single LLM call" language is the error — change to "median of K=3 concurrent calls, converging in 1 ReAct turn on [X/10] targets."
